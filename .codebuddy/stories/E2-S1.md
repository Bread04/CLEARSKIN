## Story

**As a** new user visiting ClearLah,
**I want** to see a welcoming landing page and select who I am tracking for,
**so that** the app knows how to address me and personalise subsequent copy.

4. Selected card gets primary-sage border and checkmark; "Continue" disabled until one selected
5. Selection stored in `user_profiles.tracking_for` AND localStorage

## Dev Notes

### Architecture Rules (non-negotiable)

- **AD-3 (Data Store):** Supabase is the system of record. `user_profiles.tracking_for` MUST be written to Supabase via the API route. localStorage is a read cache only — never the source of truth.
- **AD-3 (Demo bypass):** When `NEXT_PUBLIC_DEMO_MODE=true`, use `getActiveUserId()` → `DEMO_USER_ID`. The demo user row already exists in `users` table (seeded by `supabase/seed.sql`). No auth gating required in demo mode.
- **Route pattern:** Follow E1-S4's API route pattern. Client components call API routes — never call Supabase directly from browser components. Use `lib/supabase/server.ts` in API routes.

### Onboarding State Flow

```
User arrives at /

  ├── (demo mode + seed already loaded) → redirect to /dashboard
  │   (demo user has onboarding_complete: true from seed)
  │
  ├── (normal mode, profile exists + onboarding_complete: true)
  │   → redirect to /dashboard
  │
  └── (new user or demo without seed)
      → show landing page → "Get Started" → /onboarding/step/1
                                          → select tracking-for
                                          → POST /api/profile
                                          → localStorage cache
                                          → navigate to /onboarding/step/2
```

### Tracking-For Cards Design

Each card is a `button` element within a grid/stack:

```
┌─────────────────────────────────────┐
│ 🧑  Myself                          │
│     I'm tracking my own symptoms    │
│     and triggers                    │  ← unselected: border-neutral-300
│                                     │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ 👶  My child                    ✓   │
│     I'm helping my child manage     │
│     their condition                 │  ← selected: border-primary-sage
│                                     │     bg-primary-sage-50, checkmark
└─────────────────────────────────────┘
```

- Touch target: minimum 44px height per card (they're tall enough by design)
- Cards animate on selection: `transition-all duration-ui` (180ms)
- Checkmark appears with 120ms micro-animation
- `aria-pressed` on each card button; `role="radiogroup"` on container

### API Route Design (`POST /api/profile`)

```typescript
// Request body
interface ProfileUpdateRequest {
  tracking_for: "myself" | "my_child" | "someone_else";
}

// Response (200)
interface ProfileUpdateResponse {
  success: true;
  profile: {
    user_id: string;
    tracking_for: string;
  };
}

// Response (400)
interface ProfileErrorResponse {
  success: false;
  error: string;
}
```

Route follows E1-S3's pattern:
- `isFlagEnabled()`-style env parsing for `NEXT_PUBLIC_DEMO_MODE`
- `getActiveUserId()` for user resolution
- Server Supabase client via `createClient()` (async — await `cookies()`)
- `onConflict: "user_id"` for idempotent upsert
- Always returns appropriate HTTP status (never crashes to 500)
- Framework errors (digest-carrying) rethrown

### localStorage Schema

```typescript
// Key: "clearlah_onboarding"
interface OnboardingCache {
  trackingFor: "myself" | "my_child" | "someone_else";
  timestamp: number; // Date.now() when written
}
```

This cache is used only for read-optimistic UI (e.g., showing "Myself" as pre-selected on revisit) and offline resilience. Supabase is always checked on mount for the authoritative value.
