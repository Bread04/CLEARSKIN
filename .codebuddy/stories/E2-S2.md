**Epic:** E2 — Onboarding & User Profile
**Priority:** P0
baseline_commit: NO_VCS
**Status:** review

## Story

**As a** new user,
**I want** to declare my health condition(s) so tracking pillar names are personalised,
**so that** the language feels relevant to my specific situation.

---

## Acceptance Criteria

1. `/onboarding/step/2` presents multi-select condition chips: Eczema, IBS, Food allergy, Asthma, Other
2. At least one condition required; stored in `user_profiles.conditions[]`
3. Pillar label overrides applied globally post-onboarding:
   - Eczema → "Skin Flares" | IBS → "Gut Symptoms" | Asthma → "Breathing" | Food allergy → "Reactions" | Default → "Symptoms"
4. First selected condition determines pillar label when multiple selected
5. Condition chips use `PillarTag` component with `symptoms` variant

**FR Covered:** FR2, FR4

### PillarTag Component Spec (from DESIGN.md)

```
pillar-tag:
  border-radius: sm
  font: caption, font-weight 600
  padding: 0.2rem 0.5rem
  variants:
    food:      { bg: "#F2EDD9", color: "#7A5C1E" }
    lifestyle: { bg: "#DCE5F0", color: "#2D4E7A" }
    skincare:  { bg: "#EDE5F0", color: "#5E3A7A" }
    symptoms:  { bg: "#F0E5E5", color: "#7A2D2D" }
    weather:   { bg: "#DCF0F0", color: "#1E6060" }
```

Condition chips for onboarding use `symptoms` variant (all five are health conditions). Interactive variant adds `ring-2 ring-primary-sage ring-offset-1` for selected state and `cursor-pointer hover:opacity-80` for interactivity. Non-interactive variant (used in dashboard/insight cards) omits hover/ring styles and uses `role="status"`.

**Colourblind note:** Pillar colours are distinct enough for red-green colourblind users. Labels are always shown alongside colour — never colour alone design.

### Condition Label Mapping

```typescript
const CONDITION_LABEL_MAP: Record<Condition, { symptomLabel: string; promptHint: string }> = {
  eczema:       { symptomLabel: "Skin Flares",    promptHint: "skin symptoms (itching, redness, dryness)" },
  ibs:          { symptomLabel: "Gut Symptoms",    promptHint: "digestive symptoms (bloating, pain, bowel changes)" },
  food_allergy: { symptomLabel: "Reactions",        promptHint: "allergy reactions (hives, swelling, itching)" },
  asthma:       { symptomLabel: "Breathing",        promptHint: "breathing symptoms (wheeze, cough, tightness)" },
  other:        { symptomLabel: "Symptoms",         promptHint: "general symptoms" },
};
```

`getSymptomPillarLabel(conditions)` returns the `symptomLabel` of the first condition in the array, or `"Symptoms"` if the array is empty. This label replaces the generic "Symptoms" pillar name across the app (log form, insights, hawker checker).

### Profile API Route Extension

The existing `POST /api/profile` accepts `{ tracking_for }`. Extend to also accept optional `{ conditions }`:

```typescript
// Request body — both fields optional, at least one required
interface ProfileUpdateRequest {
  tracking_for?: TrackingFor;    // set by step 1
  conditions?: Condition[];      // set by step 2
}
```

The route builds the upsert object dynamically — only includes fields present in the body. This preserves `tracking_for` when step 2 calls the route without it.

```typescript
const updateData: Record<string, unknown> = { updated_at: new Date().toISOString() };
if (tracking_for !== undefined) updateData.tracking_for = tracking_for;
if (conditions !== undefined) updateData.conditions = conditions;
```

```

```
